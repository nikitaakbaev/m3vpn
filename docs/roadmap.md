# План разработки после M9

Дата: 2026-11-25

## Текущее состояние

M0–M9 закрыты. Приложение умеет:

- Xray, sing-box, AmneziaWG, Hysteria 2 и TUIC;
- горячее переключение серверов;
- Fast HTTP / TCP / HTTP GET / HTTP HEAD ping;
- сортировку списка и исключения серверов;
- TUN через привилегированный helper;
- профили маршрутизации, geo и FakeDNS для sing-box;
- импорт подписок, share-ссылок и полных конфигов;
- Arch-пакет и portable-архив;
- проверку обновлений через GitHub Releases.

## P0 — GitHub и первый релиз

Цель: публичный репозиторий, CI и воспроизводимый релиз.

| Задача | Результат |
|---|---|
| Создать публичный `owner/m3vpn` | Репозиторий доступен |
| Добавить remote и push `master` | Исходники на GitHub |
| CI: parser/helper/app, clippy, typecheck, Tauri build | Каждый push проверяется |
| Release workflow по тегу `v*` | Arch-пакет и portable tar автоматически в релизе |
| Первый тег `v0.1.1` | GitHub Release с assets |
| Проверить `check_update` с публичным репозиторием | Приложение видит релиз |

Зависимость: нужен GitHub-аккаунт и доступ (SSH-ключ или токен).

Оценка: **0.5–1 день** после появления доступа.

Критерий готовности: `git push` проходит, CI зелёный, релиз `v0.1.1` виден в приложении.

Статус: **P0 выполнен.** Репозиторий создан, CI зелёный, `v0.1.0` и `v0.1.1` опубликованы, проверка обновлений через GitHub API подтверждена.

## P1 — TUN и сеть

Цель: подтвердить, что TUN не ломает систему и корректно восстанавливается.

| Задача | Результат |
|---|---|
| TUN smoke на живой системе | Трафик идёт через `m3vpn0` |
| Проверить DNS и IPv6 | Нет утечек/зависаний |
| Проверить остановку и краш helper | Маршруты и правила восстанавливаются |
| Kill switch: fail-open/fail-closed | Явный выбор поведения |
| Очистка stale TUN при старте | Нет висящих `m3vpn0` и nft-правил |

Оценка: **1–2 дня**.

Критерий готовности: после подключения/отключения/убийства helper интернет
возвращается без ручных команд.

Статус: **P1 закрыт** в `v0.2.0`. Живой smoke прошёл: TUN использует
auto_redirect (TPROXY), front/backend обходят TUN по app-cgroup mark, UFW
пропускает `m3vpn0`, DNS и IPv6 проверены, после stop маршруты и правила
восстановлены.

## P2 — управление серверами

Цель: удобная работа с большим списком.

- массовое исключение и возврат серверов;
- фильтр «только исключённые»;
- теги/избранное;
- поиск по протоколу и ядру (`xray`, `sing-box`);
- отображение причины автопереключения;
- защита от переключения во время большого трафика;
- история пинга: график, jitter, packet loss.

Оценка: **2–3 дня**.

Статус: **P2 закрыт**; переключатель Proxy/TUN перенесён на главный экран. Готовы массовый выбор, фильтры, поиск по ядру,
причина автопереключения, теги, избранное, история пинга (sparkline), jitter,
packet loss и traffic-aware auto-switch через Clash API front-прокси.

## P3 — routing, DNS и TUN-политики

Цель: приблизиться к полноценному routing-клиенту.

- rule-set/geo-теги для sing-box;
- split tunneling по приложениям;
- отдельная IPv6-политика;
- DNS-over-HTTPS/DoQ с fallback;
- защита от DNS-утечек;
- автоподбор geo-файлов под провайдера;
- FakeDNS для Xray, если появится стабильный формат.

Оценка: **3–5 дней**.

Статус: **P3 закрыт** — sing-box geo rule-sets, TUN DNS, geo-источники,
IPv6-политика, FakeDNS Xray, split tunneling по systemd-cgroup и DNS-политика
в UI. Внешний DNS leak-test не добавлялся.

## P4 — упаковка и обновления

Цель: установка на основные Linux-дистрибутивы.

- `.deb` и `.rpm` в CI;
- AppImage;
- AUR `PKGBUILD` и публикация;
- подписанные артефакты (minisign/SHA-256);
- автоустановка обновлений через GitHub Releases;
- понятная миграция настроек между версиями.

Оценка: **2–4 дня**.

Статус: `.deb`/Arch/portable собираются из общего stage, публикуется
`SHA256SUMS`, приложение скачивает пакет с проверкой SHA-256 и ставит через
`pkexec`; Xray/sing-box обновляются отдельно из GitHub Releases. Остались
`.rpm`, AppImage, AUR, подписи артефактов и миграция настроек.

## P5 — качество и безопасность

- E2E: Playwright для UI-сценариев;
- тесты TUN/маршрутов в netns;
- проверка секретов в логах;
- отчёт диагностики без токенов;
- проверка лицензий sidecars;
- чистый smoke на Arch и Ubuntu;
- финальная документация и версия `1.0.0`.

Оценка: **2–3 дня**.

## P6 — Android (после Linux 1.0)

Цель: отдельный клиент под Android, не порт TUN-helper'а.

- Tauri 2 Android или Kotlin UI + Rust core;
- `VpnService` вместо Linux TUN;
- упаковка Xray/sing-box как Android-библиотек или локального процесса;
- foreground service, уведомление, автоперезапуск;
- per-app split tunneling;
- импорт подписок/share-ссылок, экспорт QR;
- Google Play и F-Droid.

Оценка: **4–8 недель**. Основной риск — ограничения Android на фоновые процессы
и размер нативных ядер.

## P7 — Windows (после Linux 1.0)

- Tauri 2 Windows UI;
- Wintun вместо Linux TUN;
- отдельный Windows-сервис для маршрутов, firewall и kill switch;
- подпись драйвера/установщика;
- MSI/NSIS, автообновление;
- системный прокси и per-app routing.

Оценка: **3–6 недель**. Основной риск — подпись драйвера и различия
сетевого стека.

## Порядок работ

1. **P0 GitHub** — выполнено.
2. **P1 TUN** — сейчас, критичный риск.
3. **P2 серверы** — заметная польза без внешних зависимостей.
4. **P3 routing/TUN-политики** — следующий крупный блок.
5. **P4 упаковка** — после стабилизации поведения.
6. **P5 приёмка Linux 1.0**.
7. **P6 Android** — после Linux 1.0.
8. **P7 Windows** — после Linux 1.0.

## Риски

- TUN и маршруты зависят от дистрибутива и systemd;
- GitHub Actions с Arch-контейнером тяжелее обычного CI;
- sing-box и Xray имеют разные форматы geo/routing;
- автообновление требует подписи и аккуратной работы с пакетным менеджером.

## Что не входит в Linux 1.0

- Windows и Android — отдельные этапы P6/P7;
- macOS;
- встроенный редактор произвольных Xray-конфигов;
- облачная синхронизация подписок.

Android и Windows используют общий Rust-парсер, модели серверов, формат
подписок и часть routing-кода, но требуют своих сетевых привилегированных
слоёв (`VpnService` и `Wintun`).
